# PR 7.2: 文字記一餐（AI 解析）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 使用者在聊天室打「午餐 雞腿便當 無糖豆漿」，AI 解析成品項並存成草稿，回覆 Flex 卡片；按「確認」後計入今日攝取。

**Architecture:**

- `api` 是唯一呼叫 AI 的服務（規格 §3.1）。新增 `ai/` 模組包住 `@anthropic-ai/sdk`，路由與 repo 只依賴一個介面 `MealParser`，測試注入假的實作，CI 不呼叫真的 API。
- 每日次數用新表 `ai_usage_daily` 控制。呼叫 AI **之前**先以一個 SQL 陳述原子地「檢查並加一」，並行請求也不會超過上限。
- 解析結果存成 `draft` 餐點，`source = text`，`food_id` 為 null，營養值用 AI 估的值。之後的修改、確認都沿用 7.1 的 repo。
- `bot` 判斷文字是否為記錄一餐、組 Flex 卡片、處理三個按鈕的 postback。

**Tech Stack:** 沿用 7.1；`apps/api` 新增 `@anthropic-ai/sdk`（規格 §7 指定）。不新增其他套件，JSON schema 用純物件寫，不加 zod。

**Spec:** [docs/specs/2026-10-15-gym-assistant-coach-design.md](../../specs/2026-10-15-gym-assistant-coach-design.md) §3.1、§3.3、§5 `ai_usage_daily`、§6.5、§7、§8.1、§8.4、§10 PR 7。

**前一份計畫：** [2026-10-22-pr7-1-food-logging.md](2026-10-22-pr7-1-food-logging.md)（`meals` 表、repo、LIFF 修改頁）。

## 已決定（2026-10-22，使用者同意）

1. **觸發規則：** 文字開頭是「早餐／午餐／晚餐／點心／宵夜」才當成記錄一餐。後面接空白、全形空白、`:`、`：` 或直接接食物都可以；開頭詞後面沒有內容時不算。宵夜存成 `snack`。其他文字維持現在的 `placeholder_reply`（PR 9 再改成問 AI）。
2. **不對應食藥署資料：** AI 品項 `food_id` 為 null，名稱、克數、營養值都存 AI 的估計值，並存 `ai_confidence`。使用者可在 LIFF 換成食藥署的食物。
3. **次數計算：** 呼叫 AI 之前就記一次。無法辨識、拒答都算次數。AI 服務本身出錯（逾時、5xx、連線失敗）時退回這一次。

## Global Constraints

- 使用者看得到的文字一律是繁體中文。
- 模型 `claude-haiku-5-5`，只寫在 `apps/api/src/ai/config.ts` 一個地方（規格 §7）。
- AI 呼叫：structured output（`output_config.format` 的 `json_schema`）、`output_config.effort: "low"`、系統提示放最前面並設 `cache_control: { type: "ephemeral" }`、不設 `temperature`／`top_p`／`top_k`（Haiku 5.5 會回 400）、不用 assistant prefill。
- `stop_reason === "refusal"` 時回覆通用的婉拒訊息，不重試、不設 fallback（規格 §7）。
- 每日上限：文字解析 20 次（台北日期）。超過時回覆「今天的文字記錄次數用完了，明天再試」。
- log 只記錄 token 數（input／output／cache read／cache creation）、耗時、`stop_reason`；不記錄使用者文字、AI 回傳內容或食物名稱（規格 §7、§8.4）。
- 金鑰只放 Secret Manager，注入成 `ANTHROPIC_API_KEY`。任何程式、測試、log、錯誤訊息都不能印出金鑰。
- 內部端點只接受 bot 的 Google ID token（沿用現有 `/internal/*` 驗證）。別人的餐點一律回 404。
- 營養數值格式沿用 7.1：kcal 整數，其餘小數 1 位；克數 1–2000、小數 1 位；一餐最多 30 個品項。AI 回傳超出範圍的品項要修正或丟棄，不能存進資料庫（見 Task 3）。
- 不要 stage `.claude/` 和 `skills-lock.json`。

## Review Focus

1. **並行請求超過上限**：同一使用者同時送 25 次，成功記次的最多 20 次。（Task 1 測試）
2. **AI 回傳不合法的資料**：克數 0 或 5000、熱量負數、品項 0 個或 40 個、名稱空白，都不能讓 API 回 500 或存進不合法的資料。（Task 3 測試）
3. **拒答與無法辨識**：`refusal`、`max_tokens`、AI 說「這不是食物」時，回覆對應訊息，不建立餐點。（Task 2、Task 3 測試）
4. **postback 偽造**：`action=meal_confirm&id=<別人的餐點>` 回「找不到這一餐」，資料不變；`id` 不是 UUID 時 bot 直接忽略，不呼叫 api。（Task 3、Task 5 測試）
5. **已確認的餐點再按一次「確認」**：不重複計算，回覆和第一次一樣的今日攝取。（Task 3 測試）

  ```ts

  export const MEAL_TEXT_MAX_TOKENS = 4000; // thinking 也算在內，不能太小

  // meal-parser.ts
  export interface ParsedItem { name: string; grams: number; kcal: number; proteinG: number; carbG: number; fatG: number; confidence: number; }
  export type ParseResult =
    | { kind: "items"; items: ParsedItem[]; usage: AiTokenUsage }
    | { kind: "not_food"; usage: AiTokenUsage }
    | { kind: "refused"; usage: AiTokenUsage };
  export interface MealParser { parseText(text: string): Promise<ParseResult>; }
  /** Throws MealParserUnavailable on network errors, timeouts, 429 and 5xx. */
  ```

- 請求內容：
  - `client.messages.create({ model: AI_MODEL, max_tokens: MEAL_TEXT_MAX_TOKENS, system: [{ type: "text", text: MEAL_TEXT_SYSTEM, cache_control: { type: "ephemeral" } }], messages: [{ role: "user", content: text }], output_config: { effort: "low", format: { type: "json_schema", schema: MEAL_TEXT_SCHEMA } } })`。
  - `MEAL_TEXT_SCHEMA`：`{ is_food: boolean, items: [{ name, grams, kcal, protein_g, carb_g, fat_g, confidence }] }`，全部 `required`，`additionalProperties: false`，數值是 `number`。
  - `MEAL_TEXT_SYSTEM`（`prompts.ts`，固定字串，不放日期或使用者資料，才能快取）要寫明：
    - 使用者是台灣人，用繁體中文描述一餐。
    - 每個品項估一般台灣份量的克數與營養值；飲料以毫升當克數。
    - 「無糖」「少飯」「半糖」這類描述要反映在數值上。
    - 不是食物、或看不出吃了什麼時，回 `is_food: false`、`items: []`。
    - `confidence` 是 0–1。
    - 品項名稱用使用者的說法，不超過 30 字。
    - 附 3 個 few-shot 範例（例如雞腿便當＋無糖豆漿、大冰拿鐵、「今天好累」→ 不是食物）。
- 回應處理：
  - `stop_reason === "refusal"` → `refused`。
  - `stop_reason === "max_tokens"` 或 JSON 解析失敗 → `not_food`（使用者看到「看不懂」的訊息，不建立餐點）。
  - `is_food === false` 或 `items` 為空 → `not_food`。
  - 從 `content` 找 `type === "text"` 的區塊再 `JSON.parse`（回應可能先有 `thinking` 區塊）。
  - `usage` 取 `input_tokens`、`output_tokens`、`cache_read_input_tokens ?? 0`、`cache_creation_input_tokens ?? 0`。
  - 每次呼叫 log 一行：`{ event: "ai_call", kind: "text", stopReason, ms, inputTokens, outputTokens, cacheRead, cacheCreation }`。不 log 文字或回傳內容。
  - SDK 的錯誤：`Anthropic.RateLimitError`、`Anthropic.InternalServerError`、`Anthropic.APIConnectionError`（含逾時）→ 丟 `MealParserUnavailable`。其他 `Anthropic.APIError`（例如 400、401）也丟 `MealParserUnavailable`，但 log 等級是 `error`，只記 `status`。
  - client 建立時設 `timeout: 20_000`、`maxRetries: 1`，讓整個 webhook 能在 LINE 的期限內回覆。
